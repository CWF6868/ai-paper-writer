# P0-3 LLM 调用治理层（成本故事）

> 目标不是"记个日志"，而是让每一分钱都能追到**哪个节点、哪一天、哪篇论文、哪个人**，
> 并且能据此做出可执行的动作（错峰、砍重写、提缓存命中）。
>
> 更新时间：2026-11-02　｜　代码：`app/core/llm_client.py`、`app/core/llm_log_sink.py`、`app/api/metrics.py`

---

## 一、问题：成本完全不可见

改造前的实际情况：

| 想知道什么 | 当时能不能答 |
|---|---|
| 这篇论文花了多少钱 | ❌ 没有任何 token 记录 |
| 钱花在哪个节点（大纲 / 写作 / 润色 / 评审） | ❌ 只有耗时日志，没有成本 |
| 缓存命中省了多少 | ❌ 连命中了多少都不知道 |
| 哪个用户/哪篇论文烧得最多 | ❌ 无归因维度 |
| 模型调用有没有漏计 | ❌ 没有覆盖率口径，漏了也不会有人发现 |

`app/llm/structured.py` 里已有 `llm_call_log` 的 JSON 结构化日志雏形，注释写着"表结构留到 P0-3 成本归因一起做"。这一步就是把它接上。

## 二、先纠正三条会影响全部数字的事实

计价不能靠假设。开工前核对了 DeepSeek 官方定价页与调价公告，发现三件事必须先摆出来：

### 2.1 配置里的模型名已下线，是别名

`DEEPSEEK_MODEL=deepseek-chat`，但该模型 **2026-07-24 已下线**，现在只是"仍被接受"的别名。实测响应里的 `model_name` 是 **`deepseek-flash`**（V4.1-Flash），按 Flash 计价。

→ 所以**计价一律按响应里的 `model_name` 归一化后查表，不能按配置值查**。否则查不到价，成本会静默全记 0（代码里 `priced=False` 会标记出来，但账已经错了）。

### 2.2 峰谷双价（2026-08-17 生效）

北京时间**工作日 09:00–12:00、14:00–18:00 为峰时，单价是空闲时段的 2 倍**。

→ 同一个 prompt，上午 10 点跑比晚上 8 点**贵一倍**。这是本项目里唯一"不改一行代码就能省钱"的杠杆，所以接口必须把峰谷成本拆开计量。

### 2.3 缓存命中价差 30 倍

输入侧分「缓存命中 / 未命中」两档：命中 0.05 元/百万，未命中 1.50 元/百万（空闲时段）。

→ 只记 `prompt_tokens` 不够，必须单独记 `cache_hit_tokens`，否则成本会虚高，而且看不出"评审反复塞全文"这件事其实已经被缓存救了一部分。

### 2.4 单价口径的已知分歧（不隐藏）

官方 USD 定价页与中文调价公告的数字对不上（缓存命中价差 2 倍多）。代码里两套都留了注释，**取 CNY 口径**，并在文档中标注：**以官方控制台账单为准**，可用 `.env` 覆盖。

## 三、设计：三层收口，而不是改 6 个调用点

### 3.1 为什么不能"每个 Agent 里加一行记账"

项目里的模型调用路径比看上去多：

- 6 个 Agent（topic / outline / writer / polish / reviewer / reference）
- chain 组合（`prompt | llm | parser`）
- `with_structured_output`（评审、大纲走这条，外面又包一层）
- `bind_tools`（评审图里的工具调用）

**逐个改一定漏，而且漏了没人知道。** 所以采用两层收口：

| 层 | 手段 | 作用 |
|---|---|---|
| 构造收口 | `build_chat_model()` 是唯一的 `ChatOpenAI` 出口 | 超时 / 重试 / 计量回调一处配置，不会分叉 |
| 计量收口 | `CostTrackingCallback` 挂在模型实例上 | 横切所有 invoke / ainvoke，包装层再厚也会经过模型 |

`utils/llm.py` 被收敛成薄壳，只是转调 `build_chat_model`——如果两处各自构造模型，超时和回调迟早分叉。

### 3.2 归因：contextvar 打标签

回调只知道"这次调用的 token 数"，不知道"算在哪个节点、哪篇论文"。用 `llm_scope(node=..., paper_id=..., user_id=...)` 传递，而不是给每个函数加参数。

`graph_builder` 里用 `_metered(node_name, fn)` 包装 7 个节点，**不动业务方法体**，新增节点也不会忘（漏标 = 成本表里出现 `unknown` 节点，接口里一眼能看见）。

并发安全：`contextvar` 在 `asyncio.create_task` 时会被复制，所以 P0-2 的章节并发（4 路）不会串台。

### 3.3 用户归因为什么要单独加一列

`llm_call_log` 按设计**不加外键**到 `papers`（论文删除后成本流水要留存，否则对账凭空少数）。这带来一个副作用：靠 `papers.author_id` 反查用户，会漏掉两类记录：

1. 论文已删除的历史成本 —— 流水还在，但认不出是谁的；
2. 选题推荐这类**根本没有 paper_id** 的调用 —— 它照样计费。

所以直接加 `user_id` 列，由 `llm_scope` 传入。这是"按用户看成本"能成立的前提，不是可选项。

> 老库升级注意：`create_all` 只建新表、不改已有表结构。`main.py:_ensure_llm_log_columns()` 做了轻量迁移补列；不补的话落库会因 `no such column` 全部失败，而 sink 的失败策略是"丢弃 + 计数"——表会静默停止增长。

### 3.4 超时与重试：不自建退避

- **超时 60s**（`LLM_TIMEOUT_SECONDS`）。不设时走 SDK 默认 600s，一次卡住会一直占着 P0-2 的 `Semaphore` 额度不释放，并发直接退化。
- **重试交给 SDK**（`max_retries=3`）。langchain-openai 透传给 OpenAI SDK，本身就是指数退避 + 抖动。外层再包 3 次会放大成 3×3=9 次请求——限流时反而把配额打得更狠。

## 四、计量覆盖率：100%，有独立证据

"覆盖了"不能靠感觉。用两个**独立计数源**比对：

- A：monkeypatch `ChatOpenAI._agenerate`，直接数模型被调用多少次（不管谁调的）
- B：我们的 sink 收到多少条记录

> 真实跑一篇：模型实际调用 **22 次** / 计量记录 **22 条** = **100%**，22/22 都带有效 token，0 条漏计。

这条验证的意义：如果覆盖率是 80%，成本表会**稳定少算 20%**，且永远没人发现。

## 五、落库：不能给主流程加延迟

一次生成 20+ 次模型调用。若每次同步写一次 SQLite，并发写作时会和业务写入抢写锁，直接抵掉 P0-2 的并发收益。

做法：`put_nowait` 非阻塞入队 → 后台协程每 0.5s 或攒 50 条批量提交。

| 指标 | 实测 |
|---|---|
| 单次入队 | **0.5 μs** |
| 一篇 22 次调用的落库开销 | **≈ 11 μs** |
| 一次模型调用耗时 | 1–6 **秒** |

差了 5 个数量级，可以忽略。

### 5.1 对账等式（唯一可靠的"有没有丢"证据）

```
received == written + dropped_full + dropped_no_loop + dropped_flush + pending
```

这个等式在 `stats()` 里实现，并通过 `GET /api/metrics/llm` 的 `ingest` 字段对外暴露。**它长期为 False，就说明成本表不可信**——先查丢数据，再谈成本分析。

### 5.2 两次静默丢数据（同一个坑踩了两次，值得记下来）

第一次：

```
跑完了、日志全部正常、表里 0 行
{'received': 20, 'written': 0, 'dropped_no_loop': 20}
```

探针显示回调在 `asyncio_0` 线程执行，`asyncio.get_running_loop()` 直接抛错 → 早期实现按"没有事件循环"整批丢弃。

当时的修复是"回调改继承 `AsyncCallbackHandler` 并实现 `aon_*`"，看起来解决了。**但这是误判**——第二次用没有 lifespan 的方式运行（ASGI 直连的脚本）时又整批丢了 16 条，因为真正生效的其实是 `start()` 事先绑定的 loop。

复查后的实测结论（langchain-core 0.3.63 + langchain-openai）：

```
isinstance(回调, AsyncCallbackHandler) == True
  SYNC  on_llm_end thread=asyncio_0      ← 实际走的是同步方法，且在线程池
```

**即使实现了 `aon_*`，`ainvoke` 下真正被调用的仍是同步 `on_llm_end`。** 所以修复不能依赖"记得调 `start()`"：

- `llm_scope` 在事件循环线程里调 `capture_loop()` 记住 loop（业务代码一定在循环里进入 scope）
- sink 在回调线程里回退取用这个 loop，走 `call_soon_threadsafe` 投递
- 已关闭的 loop 会被替换（脚本/测试每轮新建 loop，不刷新就一律投递失败）
- `stop()` 不用 `task.cancel()`（会打断正在提交的事务），而是投递队列哨兵，排在积压数据后面

回归测试 `test_cross_thread_without_start_lands_via_bound_loop` 锁住这个场景：**没有 `start()`、回调在线程池里，也必须落库。**

## 六、接口：`GET /api/metrics/llm`

| 参数 | 说明 |
|---|---|
| `days` | 最近 N 天（1–90，北京时间自然日） |
| `node` | 只看某个节点，用于下钻 |
| `user_id` | 仅管理员有效；普通用户传了会被**覆盖**成自己 |

三个聚合维度是三个不同的问题：`by_node`（钱花在哪一步）、`by_day`（趋势与预算）、`by_model`（有没有跑错模型 / 单价缺失）。

### 6.1 两个派生指标才是重点

- **`cache_savings`**：缓存命中相对"全部按未命中计价"省下的钱。不计量就会被当成"本来就这么便宜"。
- **`cost_if_all_peak`**：同样 token 全部落在峰时的成本。与 `cost` 之差 = **错峰省下的钱**。

  为什么不用 `peak_premium`（已发生的峰时溢价）？因为它只在"确实在峰时跑过"时才非零——晚上跑的批次它恒为 0，等于什么都没回答。反事实口径与时段无关，永远可读。

### 6.2 聚合口径的两个细节

1. **按天必须用北京时间**：峰谷价本身按北京时间划，用 UTC 分天会把北京 08:00–09:00 这段峰时算到前一天。SQL 里用 `date(created_at, '+8 hours')`，测试用"北京今天 00:30（其 UTC 日期必为昨天）"的场景锁住。
2. **派生指标按 `(model, peak)` 分组再套单价，而不是逐行算**：单价对 token 是线性的，先按同价组求和再乘单价与逐行累加等价，但只产生个位数分组，不用把上万行拉进 Python。

## 七、真实账单（2026-11-02 21:42，北京时间，空闲时段）

题目：基于检索增强生成的大语言模型幻觉缓解方法研究　｜　7 章 / 5 篇文献 / 质量分 0.44 / 60.9s

```
调用 18 次（失败 0）| 论文 1 篇
Token：输入 28,423 / 输出 12,346 / 缓存命中 8,192（命中率 28.8%）
总成本 0.086313 元 | 单篇 0.086313 元
延迟：平均 4.9s / P95 8.9s
省钱项：缓存命中省 0.011878 元 | 错峰可再省 0.086313 元（全峰时成本 0.172626 元）
落库自检：收到 18 / 写入 18 / 待写 0 / 丢弃 0 → 账平
```

| 节点 | 次数 | 输入 | 输出 | 命中 | 成本(元) | 占比 | 平均延迟 |
|---|---|---|---|---|---|---|---|
| polish_paper | 5 | 5,587 | 4,523 | 0 | 0.028734 | 33.3% | 4.4s |
| quality_check | 5 | 18,097 | 2,527 | 7,680 | 0.027381 | 31.7% | 3.3s |
| write_sections | 7 | 4,189 | 4,489 | 128 | 0.026298 | 30.5% | 6.1s |
| generate_outline | 1 | 550 | 807 | 384 | 0.003900 | 4.5% | 6.5s |

### 7.1 成本结构：输出 token 占大头

按单价拆开同一批 token：

| 项 | token | 单价（空闲） | 成本 | 占比 |
|---|---|---|---|---|
| 输出 | 12,346 | 4.50 元/百万 | 0.05556 | **64.4%** |
| 输入·未命中 | 20,231 | 1.50 元/百万 | 0.03035 | 35.2% |
| 输入·命中 | 8,192 | 0.05 元/百万 | 0.00041 | 0.5% |

**结论：成本由"生成了多少字"决定，不是由"读了多少"。** 这条直接决定优化方向：

- 重写一轮 = 多写 7–8 章 ≈ 成本接近翻倍。P0-1 把通过线从硬编码 `>=0.7` 调到 `0.44` 后，5/6 篇不再重写——**这不只是省时间，也是省一半钱**。
- 润色节点输入输出接近 1:1（5,587 → 4,523），它是"把全文重写一遍"，纯输出密集型，占 33%。

### 7.2 缓存的天花板要说清

缓存只作用于**输入**。当前命中率 28.8%，省了 0.0119 元（成本的 13.8%）。即使命中率做到 100%，输入成本也只能从 0.0308 降到 0.0012 —— 上限约省 34%。**缓存值得做，但它救不了输出成本。**

评审节点输入 18,097（占全部输入 64%）、命中 7,680（42%）——因为评审反复把同一份全文塞进 prompt，前缀高度重复。这块继续提命中率是低成本动作。

### 7.3 三次独立测量的稳定性

| 来源 | 调用次数 | 成本 | 场景 |
|---|---|---|---|
| 第 1 步（题目1，8,549 字，重写 1 次） | 22 | 0.0945 元 | 走内存 sink |
| 第 2 步（题目1，7,048 字，重写 1 次） | 16 | 0.0759 元 | 落库验证 |
| 第 3 步（7 章，重写 0 次） | 18 | 0.0863 元 | 走 HTTP 接口 |

**单篇成本稳定在 0.076–0.095 元**，随章节数与重写轮次浮动。可按 0.09 元/篇做预算口径。

## 八、代价与风险（都写出来，不藏）

| 项 | 现状 | 影响 |
|---|---|---|
| 单价口径分歧 | 官方 USD 页与中文公告数字不一致，代码取 CNY | 成本估算可能与账单有偏差，**以控制台账单为准**，可 `.env` 覆盖 |

| 批量提交在串行场景不生效 | 调用间隔数秒 > 0.5s 窗口，`flushes` ≈ 条数 | 单条事务毫秒级，影响可忽略；并发写作时才真正合并 |
| 无外键 + 无分区 | 单表持续增长 | 单机规模可接受；上量需要按月归档或加分区 |

## 十一、下一步该往哪打（基于本表数据）

1. **砍重写轮次**（最大杠杆）：重写一轮 ≈ 成本翻倍。0.44 阈值已经减少了重写，但"哪些论文值得重写"还没有策略——可以只在首检分低于某条线时重写，而不是固定 2 轮。
2. **润色分段策略**：`polish_paper` 5 次调用占 33%，输入输出 1:1。若改为"只润色质量分最低的章节"，输出量可大幅下降。
3. **评审缓存命中率**：输入占 64%，命中仅 42%。固定前缀顺序（系统提示 → 评分标准 → 全文）能进一步提高命中。
4. **错峰调度**：批处理任务（评测、批量生成）可排到空闲时段，同样的量省一半。

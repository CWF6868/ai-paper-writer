> 目标：把「6 个 Agent = 6 个大 Prompt」升级为「有类型约束、能调工具、可审计」的 Agent 层。
> 前提：不破坏现有 216 个测试的对外契约。

## 一、诊断：现在的"结构化"是字符串约定

看三个地方：

```python
# outline_agent.py:47 / reviewer_agent.py:84
outline_dict = parse_json(result) or {}      # 失败 → {}
data = parse_json(raw) or {}                 # 失败 → {}

# helpers.py:22

    return {"raw": text}                     # 静默降级，不报警

# graph_builder.py:292-298

    score, comment, dimensions = fallback_score("（评审结果解析失败，使用基础评分）")
```

**四个后果，都是真实存在的**：

| 后果 | 说明 |
|---|---|
| 假分数污染评测 | 解析失败 → 0.8，这个 0.8 会进 `eval_generate.json`、影响重写判断 |
| 维度不可聚合 | `dimension` 是自由字符串，这次叫"创新性"，下次叫"创新性与学术价值"，没法做分组统计 |
| 越界值靠手写 clamp | `score = max(0.0, min(1.0, float(raw_score)))` —— 类型系统本该拦住 |
| 字符串模糊匹配 | `_norm_section_name()` 那套正则，本质是在弥补"章节名没有受约束"这个设计缺陷 |

最后一条最典型：`graph_builder.py:17-43` 里 27 行归一化代码，全部是为了**让 LLM 输出的章节名和你的大纲标题对上**。如果章节名在生成时就被约束成枚举，这 27 行可以直接删掉。

## 二、第一层：Schema 即接口

### 2.1 目录结构

```
app/llm/
├── __init__.py
├── schemas.py       # 所有结构化输出模型（单一事实来源）
├── structured.py    # with_structured_output 封装：三级降级 + 重试 + 计量
└── tools/
    ├── __init__.py
    ├── registry.py  # 工具注册与预算控制
    ├── literature.py
    ├── citation.py
    └── text.py
```

为什么要独立 `app/llm/` 而不是塞进 `agents/`：**Schema 是跨层契约**。API 层要序列化、前端要渲染、评测脚本要断言、测试要构造 fixture。放进某个 Agent 文件里，必然被反向 import。

### 2.2 评审 Schema（核心）

```python
# app/llm/schemas.py
from enum import Enum
from typing import Literal
from pydantic import BaseModel, Field, field_validator, model_validator


class Dimension(str, Enum):
    """固定维度枚举：下游可按维度聚合，而自由文本做不到。"""
    INNOVATION = "创新性与学术价值"
    STRUCTURE = "逻辑结构与论证"
    COMPLETENESS = "内容完整度与充分性"
    LANGUAGE = "语言表达与学术规范"
    CITATION = "文献引用质量"


class Severity(str, Enum):
    BLOCKING = "blocking"   # 必须改，否则不放行
    MAJOR = "major"
    MINOR = "minor"


class DimensionScore(BaseModel):
    dimension: Dimension = Field(description="维度名称，必须从枚举中选择")
    score: float = Field(
        ge=0.0, le=1.0,
        description=(
            "该维度得分。请按以下锚点校准，不要在 0.5-0.6 之间堆积：\n"
            "0.90-1.00 达到可发表水平；0.75-0.89 小修后可投稿；"
            "0.60-0.74 需较大修改；0.40-0.59 结构或论证存在明显缺陷；"
            "0.00-0.39 基本不成立。"
        ),
    )
    comment: str = Field(description="一句话点评，必须指向具体段落或具体缺陷，禁止空泛评价")
    evidence: str = Field(
        default="",
        description="支撑该评分的原文片段（逐字摘录 15-40 字）。无法摘录时留空字符串。",
    )


class SectionFeedback(BaseModel):
    section: str = Field(description="章节标题，必须逐字抄写正文中的章标题（去掉 ## 前缀）")
    advice: str = Field(description="只针对该章节自身的问题，不要写全篇通用建议")
    severity: Severity = Field(default=Severity.MAJOR, description="该问题的严重程度")
    evidence: str = Field(default="", description="该章节中存在问题的原文片段")


class ReviewResult(BaseModel):
    score: float = Field(
        ge=0.0, le=1.0,
        description=(
            "综合质量分，必须等于 dimensions 中 5 项得分的算术平均（保留两位）。"
            "锚点：0.90+ 可发表 / 0.75 小修 / 0.60 大修 / 0.40 结构缺陷 / 0.20 不可用。"
        ),
    )
    dimensions: list[DimensionScore] = Field(description="必须恰好 5 项，每个维度一项，不得重复")
    section_feedback: list[SectionFeedback] = Field(default_factory=list)
    overall: str = Field(description="总体评价，一段话，指出最关键的 1-2 个问题")
    must_fix: list[str] = Field(
        default_factory=list,
        description="不放行就不能通过的问题清单（只列 blocking 级），用于驱动下一轮重写",
    )

    @model_validator(mode="after")
    def _check(self):
        # 1) 维度必须齐、不重
        dims = [d.dimension for d in self.dimensions]
        if len(dims) != 5 or len(set(dims)) != 5:
            raise ValueError(f"dimensions 必须恰好 5 项且不重复，实际 {dims}")

        # 2) 综合分与维度均值一致性（容差 0.03，防模型心算漂移）
        avg = sum(d.score for d in self.dimensions) / 5
        if abs(avg - self.score) > 0.03:
            self.score = round(avg, 2)   # 以维度为准，静默纠正而非报错
        return self
```

### 2.3 三个设计要点（这是和"换个写法"的区别）

**要点 1：把评分锚点写进 `Field.description`**

这一条直接解决你报告里第五节暴露的问题——"评审打分几乎全部落在 0.44-0.64，阈值 0.7 高于打分中枢，重写退化成固定动作"。

原因很朴素：原 Prompt 只说"给 0~1 之间的小数"，模型没有参照系，只能全部往中间挤（人类打分也有这个倾向，叫 central tendency bias）。给了锚点之后，模型有了刻度。

**这是用 Schema description 做 Prompt Engineering**——比在 system prompt 里堆文字更有效，因为 JSON Schema 会作为 function calling 的参数定义**逐字段**送进模型，模型的注意力更集中。

改完验收：分数标准差应该明显变大，0.44-0.64 的堆积被拉开。如果还是挤在一起，说明锚点还不够硬，改用 few-shot 锚定（在 description 里塞"例：一篇只有摘要和引言、正文空洞的论文应打 0.35"）。

**要点 2：`evidence` 字段强制可追溯**

原 Schema 只有 `comment`，模型可以写"论证不够充分"这种没法验收的话。加了 `evidence`（要求逐字摘录 15-40 字）之后：

- 前端可以高亮定位（`PaperDetail.vue` 里把 evidence 做 `mark` 标签渲染）
- 重写时能精准告诉 writer "第 3 段这句话有问题"
- 面试时可以说"评审结论 100% 可溯源到原文"——这是可解释性

**要点 3：`severity` + `must_fix` 让重写有靶子**

现在 `_pick_section_advice` 把整章建议一股脑丢给 writer，writer 不知道哪条是"不改就过不了"的。加上 severity 后，重写时只下发 `blocking`，minor 忽略。

收益：重写轮次更短、token 更省、不会因为改了小问题反而破坏结构。

### 2.4 章节名怎么办：两种方案，推荐稳的那个

**方案 A（推荐）：`str` + validator 归一化**

```python
class SectionFeedback(BaseModel):
    section: str = Field(...)

    @field_validator("section")
    @classmethod
    def _strip(cls, v: str) -> str:
        # 只做最基础的清洗，复杂匹配交给调用方
        return v.strip().lstrip("#").strip()
```

保留 `_norm_section_name` 做模糊匹配，但**把它从"猜测"降级为"兜底"**：主路径靠 Schema description 里的"必须逐字抄写"约束，匹配不上时才用归一化。

**方案 B（炫技但风险高）：动态 Literal 枚举**

```python
from typing import Literal

def build_review_schema(titles: list[str]):
    SectionName = Literal.__getitem__(tuple(titles))
    class _FB(BaseModel):
        section: SectionName
        ...
    return _FB
```

好处：模型只能从固定选项选，`_norm_section_name` 彻底删除。
坏处：章节数一多，schema 体积膨胀，DeepSeek 对复杂 schema 的遵循度会下降；而且大纲标题带"第3章"这类前缀时，枚举值本身就很脏。

**建议先做 A，把 B 记在 README 的"已知优化点"里**。面试被问到时说"我评估过动态枚举，因为 schema 膨胀和前缀污染的问题选择不用"——这个回答比直接用 B 更能证明判断力。

## 三、第二层：工具调用

### 3.1 先立规矩：什么该做成工具

这是整节最重要的一段。**大部分 Agent 项目烂在这里**——给模型挂一堆它根本不需要的工具。

三条判据，全部满足才做成工具：

| 判据 | 说明 |
|---|---|
| ① LLM 自己产不出这个信息 | 需要访问外部事实（文献库、数据库、API） |
| ② 不能用三行 Python 算出来 | 能算的，在代码里算好塞进 context，不要让模型调 |
| ③ 无副作用 | 有写操作的（发邮件、改数据）必须人工确认，不进 Agent 自动循环 |

**反例（不要做）**：

- `count_words(text)` —— 你手上就有文本，`len(re.findall(r'[\u4e00-\u9fa5]', t))` 一行搞定。让模型调工具多一次 LLM 往返，还多一份出错概率。
- `score_paper(paper)` —— 工具就是 Agent 自己的工作，循环定义。
- `write_section(title)` —— 评审 Agent 有写权限，职责越界。

正例只有一条逻辑：**评审要扣分，扣分要证据，证据在文献库里，模型看不见 → 给它一个查证工具。**

### 3.2 工具清单（4 个，不多不少）

```python
# app/llm/tools/citation.py
from pydantic import BaseModel, Field
from app.rag.vector_store import vector_store


class CitationVerdict(BaseModel):
    verdict: Literal["supported", "partial", "unsupported", "not_found"]
    similarity: float = Field(ge=0.0, le=1.0)
    reason: str


async def verify_citation(ref_index: int, claim: str) -> CitationVerdict:
    """校验正文中的论断是否被第 ref_index 条参考文献支持。

    args:
        ref_index: 参考文献编号（正文里的 [n] 的 n，从 1 开始）
        claim: 需要核验的论断原文（一句话）
    """
    refs = _current_references.get()          # contextvar 注入，见 3.4
    if not (1 <= ref_index <= len(refs)):
        return CitationVerdict(verdict="not_found", similarity=0.0, reason="文献编号越界")

    ref_text = refs[ref_index - 1].get("text", "")
    if not ref_text:
        return CitationVerdict(verdict="not_found", similarity=0.0, reason="该文献无语料正文")

    # ── 第一层：确定性初筛（不调 LLM）──
    sim = _cosine(_embed(claim), _embed(ref_text))
    overlap = _keyword_jaccard(claim, ref_text)

    if sim >= 0.72 and overlap >= 0.30:
        return CitationVerdict(verdict="supported", similarity=sim,
                               reason=f"语义相似度 {sim:.2f}，关键词重合 {overlap:.2f}")
    if sim <= 0.35:
        return CitationVerdict(verdict="unsupported", similarity=sim,
                               reason=f"语义相似度仅 {sim:.2f}，文献与论断无关")

    # ── 第二层：灰区才请 LLM 裁决（控成本的关键）──
    return await _llm_judge(claim, ref_text, sim)
```

**这里的设计亮点必须讲清楚**：工具内部**默认不调 LLM**。只有落在 `[0.35, 0.72]` 灰区才升级到 LLM 判定。按经验灰区占比 15-25%，意味着 80% 的查证是纯向量计算，耗时 <100ms。

如果每个工具内部都套一次 LLM，评审 Agent 一轮 3 次工具调用 = 3 次额外 LLM 往返，单篇耗时从 119s 涨到 150s+，**这次改造就变成负优化了**。

### 3.3 工具调用的循环设计

**渐进路径，别一步到位：**

**第一步（半天）：`create_react_agent` 跑通**

```python
from langgraph.prebuilt import create_react_agent

reviewer = create_react_agent(
    model=get_llm(temperature=0.0),
    tools=[verify_citation, search_literature],
    response_format=ReviewResult,      # 关键：让它最后产出结构化对象
)
```

先验证"模型会不会主动调工具""调了之后分数是否更准"。这一步不追求优雅。

**第二步（1-2 天）：换成显式子图**

理由：`create_react_agent` 是黑盒，你没法加**预算控制**——而这是必需的。

```python
# app/agents/reviewer_graph.py
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode

MAX_TOOL_ROUNDS = 2      # 硬上限，防止无限查证
MAX_TOOL_CALLS = 6       # 单次评审最多 6 次工具调用

def _route(state):
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None) and state.get("rounds", 0) < MAX_TOOL_ROUNDS:
        return "tools"
    return "finalize"

workflow = StateGraph(ReviewerState)
workflow.add_node("agent", _call_model)
workflow.add_node("tools", ToolNode([verify_citation, search_literature]))
workflow.add_node("finalize", _coerce_to_schema)   # 强制结构化收口
workflow.add_edge(START, "agent")
workflow.add_conditional_edges("agent", _route, {"tools": "tools", "finalize": "finalize"})
workflow.add_edge("tools", "agent")
workflow.add_edge("finalize", END)
```

**`finalize` 节点是必须的**，别省。模型调完工具后可能输出自然语言总结而不是 JSON，这一节点做最后一次 `with_structured_output` 收口，保证出口类型恒定。

### 3.4 上下文注入：别把文献列表塞进 prompt

工具需要访问"本次评审的文献列表"，但工具函数签名里不该带这个参数（模型不会填）。

解法：`contextvars`，在跑图前注入。

```python
# tools/context.py
from contextvars import ContextVar
_current_references: ContextVar[list[dict]] = ContextVar("refs", default=[])

# graph_builder._quality_check 里
token = _current_references.set(final_state.get("references") or [])
try:
    result = await reviewer_graph.ainvoke(...)
finally:
    _current_references.reset(token)
```

`contextvars` 而非全局变量：并发章节写作时（P0-2 改造后），多个协程共享全局变量会串数据。

## 四、第三层：三级降级 + 可观测

### 4.1 降级链路（`app/llm/structured.py`）

```python
async def call_structured(llm, schema, messages, *, node: str, trace_id: str):
    """三级降级：function_calling → json_mode → 裸文本解析。每一级都记录，不静默。"""
    attempts = [
        ("function_calling", dict(method="function_calling")),
        ("json_mode", dict(method="json_mode")),
        ("raw_parse", None),
    ]
    for mode, kw in attempts:
        try:
            t0 = time.perf_counter()
            structured = llm.with_structured_output(schema, include_raw=True, **(kw or {}))
            out = await structured.ainvoke(messages)
            await _log(node, mode, "ok", out, time.perf_counter() - t0)
            if out.get("parsing_error"):
                raise ValueError(str(out["parsing_error"]))
            return out["parsed"], mode
        except Exception as e:
            await _log(node, mode, "fail", None, 0.0, error=str(e))
            continue
    raise StructuredOutputError(f"{node} 三级降级全部失败")
```

**最关键的一点：兜底不能再是"静默 0.8"**。

```python
# graph_builder.py 现在的写法（要改）
except Exception as e:
    score, comment, dimensions = fallback_score(f"（评审服务异常：{e}）")

# 改成
except StructuredOutputError as e:
    logger.error("reviewer degraded", extra={"paper_id": ..., "node": "quality_check"})
    return {
        "current_step": "quality_check",
        "quality_score": None,           # 不编分数
        "quality_degraded": True,        # 新增 state 字段
        "quality_comment": f"评审不可用（{e}），本轮跳过质量门禁",
        "revision_count": revision_count + 1,
        ...
    }
```

`_check_quality` 遇到 `quality_degraded` 直接 `pass`——**放行但不假装合格**。

为什么重要：现在这个 0.8 会让"评审挂了"的论文看起来"质量良好"，然后以 `quality_score=0.8` 存进库、进入评测统计。这是**数据污染**，比功能缺失严重得多。

### 4.2 观测

结构化输出天然适合观测，因为出口有类型。加三张表（或一张宽表）：

| 表 | 字段 | 用途 |
|---|---|---|
| `llm_call_log` | node, mode(function_calling/json_mode/raw), status, tokens, latency | 降级率、成本归因（P0-3 一起做） |
| `agent_tool_log` | node, tool_name, args_hash, ok, latency_ms | 工具命中率、哪条工具最常用 |
| `review_dimension` | paper_id, dimension, score | **维度分布分析**：哪一维度长期偏低 |

最后一张表是枚举化的额外红利——原来 `dimension` 是自由文本，做不了这个分析。有了它你可以在 README 里写"过去 50 篇论文在'文献引用质量'维度平均 0.52，是系统性短板"，这是产品洞察，面试很加分。

## 五、迁移策略：不破坏 216 个测试

### 5.1 保持出口契约

现有测试大量断言 `result["data"]["score"]`。所以：

```python
# reviewer_agent.py 改造后
async def execute(self, input_data):
    result, mode = await call_structured(self.llm, ReviewResult, messages, node="reviewer")
    return {
        "raw": result.model_dump_json(),   # 兼容旧字段
        "data": result.model_dump(),       # ← 关键：dict 形状不变
        "degraded": mode != "function_calling",
    }
```

**`data` 仍然是 dict**，所以 `graph_builder.py:286` 的 `data.get("score")` 一行不用改，`test_agents.py` 里 24 个用例的断言结构也不用改。

这是最重要的迁移原则：**先换内核，保持外壳**。一次性重构接口 + 改测试，必然翻车。

### 5.2 需要新增的测试

| 测试 | 断言 |
|---|---|
| `test_review_schema_valid` | 维度缺失/重复/越界分数 → `ValidationError` |
| `test_review_avg_reconcile` | 综合分与均值偏差 >0.03 时被纠正 |
| `test_structured_fallback_chain` | mock 让 function_calling 抛错，断言降级到 json_mode 并记录 |
| `test_degraded_no_fake_score` | 三级全失败 → `quality_score is None` + `quality_degraded=True` |
| `test_citation_tool_gray_zone` | 灰区断言调了 LLM；非灰区断言**没调** |
| `test_tool_budget` | 超过 `MAX_TOOL_ROUNDS` 强制 finalize |

最后一条尤其重要：它把"成本控制"写成了测试，而不是嘴上说说。

## 八、面试话术（三个必问）

**Q：为什么用 `with_structured_output` 而不是让它输出 JSON 再解析？**

> 因为解析失败是必然事件，不是异常事件。原来 `parse_json` 失败返回 `{"raw": ...}`，下游拿不到 score 就走兜底 0.8——模型没按格式输出，系统却给了个看起来正常的分数，这个假分数会进评测集。改成 schema 约束后，格式由解码层保证，失败会显式抛错，我才知道它在失败。另外维度变成枚举之后，我可以按维度做历史聚合，这是自由文本做不到的。

**Q：工具调用为什么只有 2 个？**

> 因为工具的门槛是"LLM 自己产不出的信息"。字数统计、章节重复度这些 Python 三行就能算，我直接在节点里算好塞进 context，让模型调工具纯属浪费一次往返。只有"这条文献到底支不支持这个论断"是模型内部知识给不了的，才值得做成工具。挂一堆工具看着热闹，实际上每个都增加延迟和出错面。

**Q：加工具之后延迟不是变高了吗？**

> 是，所以我做了两件事。第一，工具内部默认不调 LLM，先算 embedding 余弦和关键词重合，只有落在 0.35-0.72 灰区才升级到大模型裁决，实测 80% 的查证是纯计算。第二，硬限两轮工具调用，超过强制 finalize。验收标准是单篇额外耗时不超过 15 秒，超了就回退重做。

## 九、一句话

> 结构化输出不是"让模型输出 JSON"，是**把模型的输出变成有类型的东西**，让错误在边界上暴露而不是在下游变成假数据。
> 工具调用不是"给 Agent 挂工具箱"，是**给模型补上它确实缺的那块外部信息**，一块就够。

# P0-2 设计：并发化 + 异步化改造

> 目标：把「端到端生成」从**纯串行等待**改成**受控并发**，把阻塞调用从事件循环里踢出去。
> 前提：不改变对外 API 契约、不改变 Prompt、不牺牲质量指标。

---

## 一、诊断：210 秒花在哪

评测基线（`data/eval_generate_v4.json`，2026-11-02，6 篇真实生成）：

| 指标 | 数值 |
|---|---|
| 平均耗时 | 210.2s / 篇（中位 205.2s） |
| 章节数 | 7–8 章 / 篇 |
| 重写轮次 | 6/6 篇均为 rev=2（首次检查 + 1 轮重写），即每篇实写 **14–16 章** |
| 每章写作 | 一次完整 LLM 往返（6–10s，800–1200 token 输出） |

三个浪费，按金额排序：

**① 章节串行（主要矛盾）**

```python
# 改造前 graph_builder._write_sections
for section in sections:
    result = await self.writer_agent.execute({...})   # 每章 6-10s，纯网络等待
    sections_content[title] = result["content"]
```

章节之间**零数据依赖**：各章拿同一批检索文献（`references` 只读）、各写自己的要点、`_pick_section_advice` 各取自己的建议。串起来写纯粹是「代码写起来顺手」，8 章串行 = 8 倍等待。重写轮再来一遍，等于把这份浪费翻倍。

**② 假异步（隐蔽）**

```python
# 改造前 retriever.search
async def search(self, query, top_k=None, filters=None):
    results = self.vector_store.search(query, top_k=k)   # 同步：embedding HTTP + Chroma 查询
```

函数挂 `async def`，里面是阻塞调用。事件循环线程被占住 ~430ms（实测），期间所有协程排队。多篇并发生成时，A 的检索直接卡住 B 的写作。讽刺的是工具层早就修过了（`app/llm/tools/citation.py` 里 `asyncio.to_thread(_embed, ...)` 还带注释），检索器是漏网的那一个。

**③ 导出阻塞（体验问题）**

`build_pdf` 实测 **636ms**（6404 字正文）。同步调用意味着任何人点一次「导出 PDF」，**整个进程**的 SSE 进度推送、列表接口全部僵死 0.6 秒。

## 二、改造一：章节写作受控并发

### 形状

```python
concurrency = max(1, int(settings.SECTION_CONCURRENCY or 1))   # 默认 4
sem = asyncio.Semaphore(concurrency)

async def _write_one(section):
    advice = _pick_section_advice(section["title"], section_feedback)   # 纯字符串运算，不占额度
    async with sem:
        return await self.writer_agent.execute({...})

results = await asyncio.gather(*[_write_one(s) for s in sections], return_exceptions=True)
```

为什么是 **4**：写作是纯网络等待，4 能把 8 章压成 2 批；再往上收益递减（8 章只需 2 批就够），却更接近 DeepSeek 单账号的并发容忍边界。可用 `.env` 的 `SECTION_CONCURRENCY` 覆盖。

### 两个必须守住的约束

**约束 1：保序回填。** `sections_content` 的**插入序就是成文序** —— `_polish_paper` 按它拼全文，`_save_results` 按它生成 `order_index`。并发后完成顺序不确定，若按完成顺序写入，论文会从「结论」开始倒着排。

```python
# 正确：按大纲下标回填
for section, content in zip(sections, results):
    sections_content[section["title"]] = content
```

测试用「第 1 章最慢、第 8 章最快」制造完全逆序完成，断言成文顺序仍是大纲顺序。

**约束 2：失败可定位。** 并发下的裸异常等于放弃排查——你只知道"某处失败"。

```python
failures = [(sections[i]["title"], r) for i, r in enumerate(results) if isinstance(r, BaseException)]
raise RuntimeError(f"章节写作失败（{len(failures)}/{len(sections)} 章）：「第2章」ValueError: rate limited") from failures[0][1]
```

`asyncio.CancelledError` 单独处理、原样上抛——否则外层无法区分「用户断开连接」和「章节写挂了」。

**约束 3（隐式）：重试预算。** 并发把在途请求从 1 抬到 4，偶发 429/5xx 的概率随之上升。不重试的话，一次限流就让整章报废，而 `gather` 会让整轮写作失败。`get_llm` 现在传 `max_retries=settings.LLM_MAX_RETRIES`（默认 3，langchain-openai 按指数退避）。

## 三、改造二：阻塞调用线程池化

| 位置 | 阻塞源 | 处理 |
|---|---|---|
| `retriever.search` | 百炼 embedding（同步 HTTP）+ Chroma 查询 | `await asyncio.to_thread(self.vector_store.search, query, k)` |
| `api/export` docx | python-docx（纯 CPU） | `await asyncio.to_thread(build_docx, paper)` |
| `api/export` pdf | fpdf2（纯 CPU） | `await asyncio.to_thread(build_pdf, paper)` |

### 跨线程前提：ORM 关系必须已加载

把 ORM 对象丢进线程后，任何**未加载**的关系访问都会炸（线程里拿不到 session）。导出路由本来就 `selectinload(Paper.references)`，但这是隐含前提，所以在派发前显式确认：

```python
list(paper.references)   # 确认已随 selectinload 加载，避免线程内触发惰性加载
```

### 诚实口径：to_thread 不加速单次导出

python-docx / fpdf2 是 CPU 密集型，GIL 挡着，线程池不会让单次导出变快（甚至多几毫秒线程调度开销）。收益只有一条：**导出期间事件循环能继续调度**（GIL 每 5ms 释放一次），其他请求和 SSE 不再被冻住。

### 怎么证明"真的没阻塞"

读代码看不出来，所以用 tick 计数：5ms 一跳的心跳协程，数被测量操作期间跑了几次。

| 场景 | 200ms 内 tick 次数 |
|---|---|
| 同步阻塞 `time.sleep(0.2)` | **0** |
| `await asyncio.to_thread(time.sleep, 0.2)` | **14** |

断言 `ticks >= 10`：宽到不怕 CI 抖动，又足以区分阻塞与未阻塞。再配合 `threading.get_ident()` 比对，双重锁定"调用发生在非事件循环线程"。

## 四、度量方法：为什么用 stub 基准测 QPS

直接用真实 API 压吞吐是错的：

1. DeepSeek 响应时延抖动 ±30%，测 3 次得 3 个数，架构差异被噪声淹没；
2. 「N 篇并发 × K 章并发」= N×K 个在途请求，测出来的是**供应商限额**，不是我们的代码；
3. 每次要花额度，做不到改一行就重跑。

所以 `scripts/bench_concurrency.py` 把 4 个 Agent 换成 `await asyncio.sleep(固定延迟)`，**前后两次跑用同一份参数**，差异只可能来自"章节写作是否并发"。

| 参数 | 值 |
|---|---|
| 每篇章节数 | 8 |
| 单次写作模拟耗时 | 1.0s |
| outline / retrieve / polish / review | 0.8 / 0.1 / 1.0 / 1.2s |
| 每级篇数 | 6 |

**QPS 口径**：吞吐 = 完成篇数 / 墙钟分钟（篇/分钟）。`--levels` 是被测的论文级并发数，每级单独计时。

## 五、实测结果

### 5.1 架构层吞吐（stub，同参数前后对比）

| 论文级并发 | 改造前 单篇 | 改造前 吞吐 | 改造后 单篇 | 改造后 吞吐 | 吞吐提升 |
|---|---|---|---|---|---|
| 1 | 11.21s | 5.35 篇/分 | 5.15s | 11.64 篇/分 | 2.18× |
| 2 | 11.21s | 10.70 篇/分 | 5.15s | 23.29 篇/分 | 2.18× |
| 4 | 11.22s | 16.05 篇/分 | 5.16s | 34.87 篇/分 | 2.17× |

写作段自身：`write_sections done: 8 sections in 2.0s (concurrency=4, serial_estimate=8.0s)`，从 8.0s 压到 2.0s（2 批）。

注意「提升倍数与论文级并发无关」是**正确**的：这次改造只动章节内并发，论文级并发能力没变。

### 5.2 端到端 6 篇（真实 DeepSeek）

**先说结论：直接拿 210.2s 对比 76.9s 是不诚实的。** 这两轮之间除了并发改造，还夹着一处配置差异（见 5.3），所以拆成三个口径报：

| 口径 | 改造前 | 改造后 | 变化 | 说明 |
|---|---|---|---|---|
| 6 篇整体 | 210.2s | **76.9s** | **−63.4%** | 混入「重写率 100%→16.7%」的结构性因素，**不能全归因并发** |
| 同一篇、同 2 轮重写（题目1） | 205.3s | 129.3s | **−37.0%** | 最接近同条件对比（章节 8→7，仍有 ±1 章噪声） |
| **每章次耗时**（归一化） | 13.8s | **8.8s** | **−35.7%** | 总耗时 ÷ (章节数 × 质检次数)，章节数与重写轮次都解耦 |

两个独立口径（同题目 −37.0%、归一化 −35.7%）互相印证：**并发净效果约 −36%**。

逐篇明细：

| id | V4 耗时 | V5 耗时 | 变化 | V4 章×轮 | V5 章×轮 | V4 质量 | V5 质量 |
|---|---|---|---|---|---|---|---|
| 1 | 205.3 | 129.3 | −37.0% | 8×2 | 7×2 | 0.510 | 0.520 |
| 2 | 222.9 | 66.3 | −70.3% | 8×2 | 8×1 | —（降级） | 0.530 |
| 3 | 218.7 | 67.4 | −69.2% | 8×2 | 8×1 | 0.440 | 0.440 |
| 4 | 204.9 | 68.7 | −66.5% | 7×2 | 7×1 | 0.440 | 0.440 |
| 5 | 205.0 | 59.9 | −70.8% | 7×2 | 7×1 | 0.440 | 0.440 |
| 6 | 204.7 | 70.0 | −65.8% | 8×2 | 8×1 | 0.420 | 0.440 |

合计 1261.5s → 461.6s。中位 205.2s → 68.1s。

### 5.3 那 63% 里有多少是假的：配置差异披露

`V4` 是 **11-02 10:36** 跑的；`QUALITY_PASS_THRESHOLD=0.44` 是 **14:53 的提交（3234b6f）** 才落地的。此前判定逻辑是硬编码：

```python
# graph_builder.py:343（3234b6f 之前）
if state.get("quality_score", 0) >= 0.7:
```

V4 的 6 篇首检分是 0.42 / 0.52 / 0.44 / 0.44 / 0.42 / 0.42 —— **全部低于 0.7 → 100% 重写**，每篇多写 7–8 章。V5 用 0.44，首检 0.44 即通过 → 5/6 篇一次过。

所以「重写率 100% → 16.7%」是**阈值变更**的结果，与并发无关。这也是为什么必须用 5.2 的后两个口径（同条件、归一化）来报并发的净效果。**如果只报 −63.4%，就是拿配置差异冒充性能优化。**

### 5.4 质量核对：有没有拿质量换速度

| 指标 | V4 | V5 | 差异 | 判断 |
|---|---|---|---|---|
| 平均质量分 | 0.450 | 0.468 | +0.018 | 在评分噪声带 ±0.02 内 |
| 平均字数 | 10205 | 9097 | −10.9% | **超 ±10% 阈值，需解释**：主因是少一轮重写；同条件（题目1，同为 2 轮）9619 → 9191，仅 −4.4%，在噪声带内 |
| RAG 引用命中 | 5.0 条/篇 | 5.0 条/篇 | 0 | 不变 |
| 正文引用标注 | 5.0 处/篇 | 5.0 处/篇 | 0 | 编号 1–5 全覆盖，无错位 |
| 评审降级篇数 | 1（题目2） | 0 | −1 | — |

结论：**并发没有把质量换成速度**。字数下降可由「重写轮次减少」解释（重写会重写全部章节并普遍加长），不是并发把章节写短了。

### 5.5 为什么不是 4 倍：固定段吃掉了上限

单篇耗时 = 固定段 + 写作段。固定段包含大纲、润色、评审 —— 都**不可并发化**：润色依赖全部章节写完，评审依赖全文，且评审内部还有工具调用往返。

用题目 1 的两次运行反解（同题、同 2 轮重写）：

- V4：16 次章节写作**串行** → `16w + F = 205.3`
- V5：14 次写作、并发 4（每轮 7 章 = 2 批，2 轮共 4 批）→ `4w + F = 129.3`

解得 `w ≈ 6.3s/章`，`F ≈ 104s`。

也就是说**约 104s 的固定段完全不受并发影响**，这决定了单篇下限：写作段再快，也压不到 104s 以下（估算，含 ±1 章噪声与工具调用耗时）。下一步的优化空间不在写作段，而在：

1. 润色与评审的串行（润色可以按章节并行做局部润色，但会牺牲全文一致性）；
2. 评审工具往返（9 次/篇的查证调用，多数可以合并或跳过灰区）；
3. 重写轮次（首检分集中说明瓶颈在生成同质性，不在门禁）。

## 六、代价与风险

| 风险 | 说明 | 处置 |
|---|---|---|
| 在途请求放大 | `SECTION_CONCURRENCY` 是**每篇**上限，K 篇同时生成时进程内在途 ≈ K×4 | 写进 config 注释；多用户部署按账号配额调小 |
| 质量漂移 | 同轮章节不再"看到"彼此的措辞，跨章衔接可能略松 | 5.2 对比质量分/字数/引用数，超噪声带如实记录 |
| 429 限流 | 并发抬高后概率上升 | `max_retries=3` + 指数退避 |
| 跨线程 ORM | 若将来在导出前加了 commit，对象 expire，线程内读属性会炸 | 已在派发前强制加载关系；彻底方案是快照成 plain dict（未做） |
| 线程池上限 | `asyncio.to_thread` 用默认 executor（min(32, CPU+4)），导出洪峰可能排队 | 当前用量远低于上限，暂不调 |

**明确没做的**：

- 跨篇共享全局 Semaphore（会牺牲单篇延迟，与"单用户单篇生成"的产品形态不符）
- 把 `sections_content` 改成显式有序结构（`list[tuple]`）—— 插入序约定已被测试锁住，改结构收益为零、影响面大
- writer 的流式输出（`stream_execute` 已有，但工作流没用）
